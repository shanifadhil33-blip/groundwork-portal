# Database operations

Use `pnpm db:reset` to apply pending migrations and replace all development data with fictional fixtures. It connects only through `DATABASE_URL_OWNER`; `pnpm db:seed` also resets the entire fixture database, including auth tables. These commands are for development, never a populated production database. `pnpm db:migrate` applies unapplied numbered SQL files without resetting data.

The app login (`APP_DB_ROLE`, default `portal_app`) must already be provisioned with its own password on managed Postgres. A migration owner with role-creation permission can create a missing NOLOGIN role, which still needs separate login provisioning. The migration runner rejects administrative app privileges and all app role memberships. Keep the app role separate from the schema owner.

Every table has ENABLE and FORCE RLS. Explicit policies assigned to the migration owner allow seeding, auth adapter operations, and SECURITY DEFINER membership/audit/timeline functions to work even when the owner has no BYPASSRLS privilege. The app role receives no access to auth tables, no schema CREATE, no TRUNCATE, and only SELECT on the audit log and timeline. Notifications allow SELECT plus UPDATE of read_at only. Supplier mutations require admin; internal import records require staff or admin.

Tenant access goes through `withUser(userId, fn)`, which sets transaction-local app.user_id, commits or rolls back, and releases the connection. `withSystem(fn)` is reserved for migrations/seed, Auth.js adapter operations, and later documented webhook/cron jobs. No identity means zero tenant rows. Never expose arbitrary user ids or owner queries through route inputs.

Auth.js adapter columns follow the [official pg adapter schema](https://authjs.dev/getting-started/adapters/pg), with UUID keys replacing SERIAL and corresponding UUID userId foreign keys. Auth tables have no app policies or grants. Google auth routes are outside Batch 1.

`pnpm test` requires separate TEST_DATABASE_URL_OWNER and TEST_DATABASE_URL databases. Global setup refuses the development database, resets only the test public schema, migrates and seeds once. Tests run serially in one fork; assertions use the app connection. Secrets stay in the ignored .env.local file.

Milestone 2 adds FORCE-RLS `idempotency_keys`, scoped to the current user; the app has SELECT/INSERT only. Narrow SECURITY DEFINER functions bootstrap a workspace/admin membership, accept a matching invite capability, delete a confirmed workspace's dependent data, remove a member's assignments/notifications, and expose only permitted identity/assignee fields. They read identity from transaction-local context and use fixed search paths; they do not accept a caller user id. Regular tenant services continue to use only the app connection. Auth adapter operations continue to use the owner pool. New status notifications run in an owner-policy trigger alongside existing audit/timeline triggers. Work-order versions advance monotonically with millisecond precision. Invite acceptance stores `accepted_by` and uses row locks for replay and state transitions.

Test global setup resets/migrates the separate test database once; each serial test file reseeds its fixtures so results do not depend on file order.

Migration `0005_supplier_sync.sql` adds the simulated supplier's independent source tables: `cobalt_state` (workspace primary key, bigint sequence, outage), `cobalt_orders` (unique cobalt_ref, workspace/work-order identifiers, supplier status), and `cobalt_events` (globally unique event_id, unique workspace/sequence, status, occurred_at, dropped). These represent a **simulated supplier, part of this repo**, separate from portal projections. Source orders deliberately retain external work-order identifiers without a work-order FK; their workspace FK cascades for workspace deletion. Source events cascade with their source order. The migration bootstraps source orders from existing portal rows without inventing historical events.

Portal `supplier_orders.last_sequence` tracks the latest applied source sequence; `supplier_events.sequence` is nullable for legacy receipts. Its existing globally unique event_id enforces delivery deduplication. `supplier_sync_runs` records workspace, trigger manual/cron, operation check/repair, start/finish, mismatch/order repair counts, ok/error status and a sanitized plain error. Runs cascade on workspace deletion. All four new tables have ENABLE/FORCE RLS, owner policies, staff/admin read policies, and app SELECT grants only. The app cannot directly mutate source state or sync runs. Existing supplier mutation policies remain admin-only; the explicitly authorized staff placement service is a system capability.

`withSystem` now also serves verified signed webhook ingest, cron, and the narrowly scoped simulator/manual sync services. Manual services first authorize using `withUser`, then recheck membership inside their system transaction and set the authenticated user's context for audit attribution. Client/missing membership is neutral 404; admin operations reject staff with 403. Webhooks trust only HMAC authentication and validate workspace/ref together against a local supplier row; cron trusts only its bearer secret. Neither accepts an arbitrary caller identity. Owner access never backs generic tenant reads. Webhooks/cron have null audit actor; manual repair uses the actual admin.

Per-workspace transaction advisory locking serializes simulator mutations, event ingestion, checks and repairs; the source counter allocates monotonic workspace sequences. A source event commits before a simulator webhook attempt. Receipt insert uses ON CONFLICT(event_id) DO NOTHING; duplicates exit before projection updates. Older sequence events cannot regress the projection; delivered/cancelled remain terminal. Delivery resumes waiting_on_parts to in_progress, using existing status timeline/audit/notification triggers. Repairs ingest missing receipts with received_via=reconcile and append one `supplier_repaired` timeline row with `Repaired by sync`. Existing audit triggers cover this row too. A repeat repair only adds a sync-run record, with no new business audit/events/notifications. Projection drift can also be repaired when receipt ids are already complete.

Check changes only its sync-run record. Each check/repair creates its run before processing; processing and finished success counts commit with business changes. Failures roll back business changes and finish the run as error in a separate transaction. A terminated process may leave a run unfinished; dashboard uses finished_at only. Run rows deliberately have no business audit trigger so recording an idempotent repair attempt cannot itself create audit rows. Dashboard last sync now uses these runs rather than webhook receipt timestamps.

The four seeded orders have matching Cobalt source state and sequenced initial receipts. The fourth portal order is shipped with a waiting-on-parts work order; Cobalt is delivered and its `demo-delivered-4` event is marked dropped and absent locally. Thus a fresh demo has exactly one mismatch. Both fixture workspaces still have their original work-order counts. Development migration does not reset existing fixtures; use the documented development seed/reset command when a fresh demo fixture is wanted. `COBALT_WEBHOOK_SECRET` and `CRON_SECRET` are already listed by name in `.env.example`; actual values remain only in ignored local/deployment settings.

Migration `0006_settings.sql` adds FORCE-RLS `user_preferences`: user_id primary key/FK to users (cascade), theme checked to light/dark/system (default system), email_notifications boolean (default true), nullable timezone override, and updated_at. App SELECT/INSERT/UPDATE is restricted by the own-user policy. Preference writes set updated_at using the database clock. Lazy initialization is conflict-safe; preferences and profile have no workspace audit trigger.

The users table now permits the app to SELECT only id/name/email/image and UPDATE only name, with self-only SELECT/UPDATE RLS. Other users remain accessible solely through the existing narrow visible_user helper; accounts, sessions, verification tokens, and sensitive auth fields remain inaccessible. This is the explicit exception to the earlier statement that all auth tables lack app grants.

Notifications gain `entity` (default work_orders) and an unread partial index on user_id/workspace_id. Existing recipient-plus-membership RLS remains unchanged, as does the column-level UPDATE(read_at) grant. Services use app-role RLS joins to decide whether a link target is visible. Counts across workspaces use the same RLS without owner access. No event/fixture spam is added.

The existing audit_log_read policy was verified: admins see their workspace, staff see only actor_id=app_user_id(), clients see none. No policy tightening was necessary. App access remains SELECT only; tests prove INSERT/UPDATE/DELETE fail with insufficient privilege. Audit snapshots are recursively redacted at the API boundary, while stored history remains intact. Existing business triggers cover workspace settings and batches 2–4 write paths; system rows retain null actor. Read receipts continue to use the existing notification audit trigger. Workspace settings/delete reuse Batch 2 operations and require no duplicate schema or deletion capability.

Migration `0007_demo_sandboxes.sql` adds `users.is_demo` and `demo_workspace_id` and `demo_persona` (all populated together; persona remains stable across profile-name changes), a partial workspace expiry index, and FORCE-RLS owner-only `demo_creation_attempts` with HMAC IP hash/time index. Existing fixtures previously labelled demo without an expiry are converted to real workspaces. The shared builder in `lib/fixture.ts` now serves both `scripts/seed.ts` and sandbox creation; seed creates the same stable real Ridgeline/Summit ids/counts, while sandbox creation uses random ids, reserved `@demo.groundwork.invalid` emails, workspace-prefixed supplier/event ids, and relative dates. Development seed clears rate records too.

Membership insert/update triggers require matching real/demo flags; demo users are bound to exactly their `demo_workspace_id`, preventing cross-sandbox membership too. Flags cannot be changed. Invite insert/update rejects demo target emails and demo workspaces, including owner operations. Accounts insert/update rejects demo user ids, and no demo accounts are created. Users' new flags/binding remain owner-only columns. Session insert/update caps a demo session's expiry to its workspace deadline, including Auth.js renewal. Request authentication resolves cookies through the actual pg adapter and checks both session and demo workspace expiry; no production header or test identity bypass is enabled.

Narrow app-granted wrappers for create_workspace/accept_invite/delete_workspace/remove_member reject demo callers. Previous implementations are renamed and their app grants explicitly revoked, preventing bypass. `require_real_user()` is available to app services and invocation-context management triggers; direct app membership/invite mutation and workspace deletion reject demo actors. The owner retains authorized lifecycle access. App role cannot run the owner-only delete_demo_workspace or underlying deletion implementation.

`withSystem` is explicitly authorized for public sandbox creation/rate enforcement, demo session rotation/reset, owner-only cleanup, and isolation target metadata lookup. A global transaction advisory lock serializes sandbox lifecycle/cap/rate/cleanup operations. Every creation/reset inserts workspace, identities, fixture data and database session atomically; errors roll everything back. Isolation work-order queries always run as the app role in `withUser`, with id-only params. Existing membership/client RLS continues to isolate real users from demos and one visitor from another, with tests through the real session lookup and non-owner role.

Cleanup uses owner-only `delete_demo_workspace(uuid)`, which locks/checks a demo workspace and reuses the previous ordered workspace-deletion implementation. It then deletes demo audit rows and idempotency keys before demo identities; auth sessions/accounts/preferences cascade on user deletion, while Cobalt source/sync rows cascade with workspace deletion. Demo audit history may be deleted; real workspace audit retention is unchanged. Cleanup is idempotent, selects only expired demo workspaces, returns deleted workspace/user/session counts, and prunes rate hashes older than one hour. Reset uses the same deletion path and creates a replacement workspace with a new id/persona session and 24-hour deadline in the same transaction.

Daily demo cleanup runs at 04:00 UTC and start opportunistically clears up to ten expired sandboxes. Existing supplier cron now excludes demos so their dropped delivery remains repairable; manual sync/webhook behavior remains scoped as before. Tests verify cleanup preserves live demos and both real fixture workspaces, DB membership/account guards, cap concurrency, transaction rollback, session invalidation, client/cross-workspace RLS, and denied owner-function access.

## Migration 0008 — agent access

`0008_agent_access.sql` adds `api_tokens`: UUID id, workspace_id/user_id with cascading workspace/user foreign keys, 1–80-character name, display token_prefix, unique 64-hex-character SHA-256 token_hash, read/write scope, created_at, nullable expires_at, last_used_at and revoked_at. Membership is checked live rather than retained as a role snapshot or foreign key: a removed member's token remains revoked by lack of membership; role/client changes apply immediately. A narrow SECURITY DEFINER `verify_api_token(text)` looks up only the digest and returns validated identity/workspace/scope/name metadata, joining current membership and checking token and sandbox expiry. It updates last_used_at at most every five minutes. This capability bootstrap uses the app pool; it never reads tenant business data. Fixed search_path and revoked PUBLIC execution protect both this helper and `cap_agent_token()`; the latter forces demo issuance to expire within 24 hours and the sandbox deadline.

Token RLS is ENABLED and FORCED: members select own tokens, admins may select all within their workspace; INSERT requires the caller's own identity and current membership; UPDATE permits owner/admin in a current workspace. App grants allow SELECT/INSERT and only UPDATE(revoked_at), preventing mutation of identity/hash/scope/expiry through the ordinary app role. Owner policy supports migration/cleanup. Session-only services explicitly select safe columns and generate plaintext once; no route returns hashes. Audit trigger includes token management, stripping token_hash from stored before/after snapshots. Plaintext is never persisted in a token, replay record or audit snapshot.

`assistant_actions` has UUID id, cascading workspace_id/user_id, tool text, args jsonb, created_at, expires_at (default ten minutes) and consumed_at. FORCE RLS SELECT/INSERT/UPDATE checks the caller owns the row and is still a workspace member; admins cannot confirm another user's action. Owner policy supports cleanup. Confirm uses row locking, service execution and consumption in one `withUser` transaction; nested same-user service calls reuse that transaction under AsyncLocalStorage. No provider call happens while holding the confirmation lock. A replay returns 409; errors that abort SQL roll back the whole transaction. Pending actions are proposals rather than business writes, so this staging table has no audit trigger. Expired rows may remain stored until workspace/user deletion; there is no periodic pending-action pruning yet.

`audit_log` adds actor_kind (`user` default, `agent`, `assistant`), nullable via_token_id and via_token_name. Token attribution is a snapshot without a foreign key so retained real-workspace audit history survives token/workspace removal. Existing capture_audit reads transaction-local app.actor_kind/app.via_token; actor_id continues to use app.user_id. Token writes use agent and token id/name; confirmed assistant writes use assistant and no token; session behavior stays user. Existing audit access/grants and recursive API snapshot redaction remain unchanged. Hashes and plaintext never appear in dedicated attribution columns.

Migration runner grants the app only required token/action access and verify helper execution. Cascades integrate both tables with real workspace deletion, demo reset and expired sandbox cleanup without owner shortcuts in any tool path. No new environment variables or dependencies are required.

## Work order dates and numbering — migration 0010

`work_orders.due_on` is a nullable Postgres date, separate from the visit timestamp `scheduled_for`. Existing scheduled days are copied using each workspace timezone. The pg date parser returns calendar strings without timezone conversion. Open orders with a recorded visit are promoted to Scheduled.

`order_number` is positive, permanent, and unique per workspace. Existing displayed numbers are retained where unique; unnumbered records receive the next number. An owner-only, FORCE-RLS `work_order_counters` table and transactional insert trigger allocate numbers for all sources, including concurrent creates/import approvals. Counters follow workspace deletion and are never exposed to the app role. Owner fixtures can supply stable numbers.

A database guard rejects app edits/deletion of Done orders, except an admin status-only reopen (Scheduled with a visit, otherwise Open); comments remain separate and writable under their existing RLS. The service additionally requires explicit `reopen:true` and the current version. Client insert RLS prohibits staff-controlled due dates. Owner maintenance and the existing authorized workspace/member removal functions remain supported. Timeline `details` records named assignments, visit instants, calendar deadlines, changed request details, and previous/new statuses. Creation events use the record creation timestamp.
